# 拒绝关门幻想：「素描模特原则」与行业最佳实践四步寻源手册

> **为什么要把“看可靠开源代码”写进研发硬流程，又为什么禁止未经授权直接搬运？**
> 一句话讲透——**「素描模特原则（The Sketch-Model Principle）」**：
>
> - **允许并鼓励先对照可靠开源代码的结构**：如果当前研究的东西在业界有明确可靠的开源代码，先去阅读并拆解对方的代码结构、模块分层、状态机与边界容错，评估是否适用于自己的场景。开源代码的存在本身，能极大降低 AI 写代码时的幻觉概率——它就像**画画时摆在面前的“素描模特”**，让你照着真实世界跑通的比例和结构落笔，而不是凭自己脑子凭空脑补现实中不存在的东西。
> - **原则上，除非用户明确授权，绝不直接引用、复制或把别人的开源代码当依赖引入自家仓库**：只学骨骼、不偷皮肉（既严守开源许可证与供应链安全边界，也避免把外部项目的历史包袱和本地不存在的“虚幻接口”搬进自家代码库）。

凡涉及核心架构设计、关键缺陷升维整改、经典 Agent Harness 机制（回合生命周期、取消与队列、向人发问与超时、权限审批、上下文压缩、记忆与技能加载、子代理协作）或重要提示词编写，**动笔前必须走完以下四步寻源法**。

---

## 第 1 步：先翻本项目已授权底层底座 / 框架的「真实源码」（能复用 0 行自研）

- **绝不只信二手文档、博客或脑海里的旧记忆**：直接定位到 `node_modules` / 已授权依赖仓 / 框架源码目录，翻看真实类型声明（`.d.ts` / `.pyi`）与核心实现代码。
- **重点查清四件事**：
  1. 底座是不是早就原生自带这项能力（或通过一个配置项就能开启）？
  2. 底座留了哪些官方扩展点 / 生命周期钩子 / 事件总线？
  3. 底座的契约测试（Contract Tests）在哪里？我们写完适配器必须原样跑通它的契约测试。
  4. **替换模块硬纪律**：如果确需用自研模块替换某个官方内置模块，必须先**通读被替换模块 100% 的源码**（全部公开/隐式方法、订阅了哪些事件、卸载时销毁哪些资源），严禁漏接隐形副作用。

---

## 第 2 步：找明确可靠的行业开源代码当「素描模特」（图谱找路，源码拍板）

针对你要解决的问题领域，寻找经过真实流量检验的高质量开源项目作为“素描模特”，评估其结构是否适用：

| 问题类型 | 优先参考的“素描模特”方向 | 重点拆解与评估什么 |
| :--- | :--- | :--- |
| **Agent Harness / 工具循环 / 上下文压缩 / 技能与记忆** | Claude Code / Anthropic 官方工程范本与提示词体系、头部开源 Agent Harness（如 DeepSeek Harness / OpenCode / LangGraph / Vercel AI SDK） | 回合状态机如何做中断修复、Tool-Result Clearing 如何防上下文腐烂、提示词如何停在黄金海拔防过度触发 |
| **数据库隔离 / 并发锁 / 账本幂等** | PostgreSQL 官方 `FORCE RLS` 与租约锁范式、支付级两阶段冻结/结算开源参考实现 | 崩溃后冻结如何回收、如何防止并发扣款余额倒跳、为何不把缓存版本号误当乐观锁 |
| **前端交互与实时流同步** | 主流前端框架官方并发与状态管理范本（React / TanStack Query / SSE 断连重连实现） | 加载态/错误态/空态/真 0 四态严格分离、事件名共享与视图刷新映射表、流式秒停清理 |

### 高效拆解“素描模特”的实战技巧
- 可将本地参考开源仓通过 `code-review-graph register <路径>` 注册进图谱并生成轻量 Wiki，几秒钟定位到关键调用链；
- **铁律**：图谱和摘要只用来定位——**必须打开对应行号的真实源码亲自逐行阅读**，再结合自己的产品蓝图客观评估：**哪些结构适用？哪些是对方特定背景下的包袱、本项目绝不能照搬？**

---

## 第 3 步：借鉴的两条硬红线（零未授权搬运 · 零虚幻接口）

看完“素描模特”准备落笔时，严守两条边界：

1. **严禁未经用户明确授权直接引用或复制外部开源代码**：
   - 默认只借鉴其**结构设计、职责切分、状态机与容错思想**，在本项目自己的架构与协议约束下独立原创实现；
   - 如果评估后认为直接引入某个开源包或复用某段开源代码性价比极高，**必须停手列出该项目的许可证（MIT / Apache-2.0 / GPL 等）、维护活跃度与接入代价，经用户明确授权后方可引入**。
2. **提示词「先忠后改」，代码「逐接口核实本仓」**：
   - 借鉴公开行业最佳提示词设计思想时，优先忠于经过验证的清晰分层与动机写法，再做最小化本地业务适配；
   - 落笔写代码时，**每一个调用的函数名、事件名、配置项与数据库字段都必须对照本仓真源码与 `PROTOCOL_FIELDS.md` 逐一核实**，绝不照抄出本仓压根不存在的“虚幻接口”。

---

## 第 4 步：外部权威检索交叉验证 + 在 PR 中明示「素描模特对照结论」

- 对照完参考源码后，针对关键假设（如是否扛得住 100 倍真实量级、是否存在跨平台兼容坑）做一轮权威文档交叉核实；
- **强制留档输出（写入 PR 模板第 2 节，供独立审码官查验）**：单列 3–5 行 **`底座与素描模特对照结论`**：
  1. 查了哪份底层底座真源码 / 哪份可靠开源“素描模特”；
  2. 评估后借鉴了什么结构思想、为什么舍弃了对方不适合本项目的部分；
  3. 明确声明：除用户已授权底座外，零未经授权的外部代码直接搬运或新增依赖。
  *(凡经典核心问题拿不出对照结论的闭门空想方案，独立审码官可直接打回。)*
