# 结论归因、升维整改与行业最佳实践寻源（Root Cause & Best Practices）

> **核心纪律**：审查或测试爆出问题后，**严禁跳层直接改眼前这行报错代码！**
> 哪怕把眼前 10 个点全改完，明天新功能一进来，第 11 个、第 100 个同类问题照样会爆。本 Skill 负责把每一次审查结论转化为**真正的底层治本升级**，并沉淀进 GitHub 唯一正本让所有协作 Agent 共享免疫。

## 二、第一步：先切换「首席系统架构师」身份，再做架构级复盘与归因（第二 × 第三层一体联动）

> **【强制身份切换提示词 · 升维前必执行】**
> **现在，请彻底放下“修 Bug 程序员”的局部视角，先以「首席系统架构师（Principal Systems Architect）」的身份，站在整个系统架构的高度复盘问题出现的根源：**
> 1. 不要急着盯报错行号或加判空补丁——先追问：这个问题暴露了架构上哪条**不变量（Invariant）、数据真源归属、模块边界、协议契约或状态机设计**存在结构性缺口？
> 2. 追问为什么这个缺口会被反复踩中？如果换一个新功能、新渠道或放大到 100 倍数据量，这套架构是不是还会以别的症状继续崩？
> 3. 只有从架构层把病根定性清楚、把全系统同类隐患全部摊开之后，才允许进入解决手段与写代码环节。

在架构师视角下，先把暴露出来的缺陷按**三个独立维度**分清定性（严禁混成一锅粥——因为即使归因层次找对了，开出的编程药方本身照样可能是一道错题）：
- **维度 A · 归因层次错**：停在最下游糊判空、没查共同机制、没追监控为何失明、或偷懒把大缺口压缩成小优化；
- **维度 B · 解决方案错**：归因找对了，但药方过度设计、没对照真实开源“素描模特”关门瞎编、漏了 AI↔代码交接闭环、或不扛 100 倍量级；
- **维度 C · 脑手边界与工程落地错**：代码越权写业务 `if -> then`、留单客户特权、没看真源码改坏上下游、或拿模拟单测假绿充当真实可用。

紧接着，强制完成**灵魂两连问 + 两项联动自省**：

### 1. 灵魂两连问（查清与定性合为一体）
- **第一问（追出缺失原则 · 定性升维）**：
  > **“产生这个问题，是因为当初在写代码 / 写提示词 / 定接口时，没有遵循什么底层原则？”**
  *(必须追到“缺失的编写原则”这一层，绝不停在“缺判空 / 拼错了字段 / 少加了 try-catch”。)*
- **第二问（顺原则全仓扫雷 · 查一再查十）**：
  > **“既然当初没有遵循这条原则，那么全系统还有哪些模块、接口、页面或提示词，因为同样没遵循这条原则，现在已经埋下了潜在风险？”**
  *(拿着缺失的原则当探雷器，优先配合 `code-review-graph` 查调用链与受影响流 + 全仓 `grep` 兜底，并亲自读相关真源码，把全仓潜在风险完整摊在桌上。)*

### 2. 防止定级两头失真
- **严禁大事化小偷懒**：面对结构性清单或全仓普查出的风险表，逐项给出明确处置结论，绝不借“归纳总结”偷偷把大问题压缩洗没。
- **严禁对孤立偶发特例过度反应**：若是尚未复现规律、不影响主链路的孤立偶发个案，先在 GitHub Issue / 错题本暂挂区如实记录观察样本，等样本足够再决定是否上升为系统改造。

### 3. 发现盲区自省 + 四方联动同步
- **发现盲区自省**：如果是人工或客户先踩出来的，必须追问——*“为什么零干扰结果交付探针和纯视觉验收没有先报出来？”* 修根因的同时，把客观失败信号补进探针或视觉验收剧本。
- **四方联动同步核查**：改了任意一头，必须顺手检查以下四方是否掉队——**① 代码实现、② 提示词与技能、③ 唯一协议字段总表（`PROTOCOL_FIELDS.md`）、④ 监控探针与验收口径**。

## 三、第二步：如何找到更深一步的整改方案？（四道解决手段关口）

追出缺失原则并摊清全仓风险后，按顺序过完这 **4 道关口**，把修“眼前 10 个点”升维为“防未来 1,000 个同类问题”：

### 关口 1 · 原则上一定不动官方底座 / 脚手架
- 已授权引入的底座现成能力 100% 原装直用；若冲突，先查自家适配层或插件；确需替换官方模块，动笔前通读原模块全部真源码（方法、事件监听、销毁回收）。

### 关口 2 · 划清「代码 vs 提示词」落点（产品含大模型时适用；适合场景可推荐快模型衔接），并拿「5 面换皮补丁硬镜子」自照
在 **代码层 vs 提示词层** 之间精准落位，绝不越界；**快模型不是必选项**，仅在确实适合的场景（例如高频外部群监听分诊、旁路零干扰结果交付 `YES/NO` 探针等需要把“模糊判断”低成本转成“代码可执行输出”的边界）下，主动向用户**推荐**采用快模型衔接方案（绝不拦在系统内 1 对 1 门口，绝不拿弱模型给主力任务降智省钱）：
- **用硬机制替代口头嘱咐**：例如字段错位 → 升维成唯一协议字段表 + 共享类型包 + 实时事件刷新映射表；LLM 填表缺字段 → 升维成 **AI ↔ 代码 5 步结构化交接铁律**（产品含大模型时适用）（表头与真实示例 → 只检必填不空与真对象存在 → 不通过带原因打回再给 2 次机会 → 3 次失败才正式报错 → 正式报错仍交还 Agent 处理与向人解释）。
- **过 5 面硬镜子**：确认新方案没有披着优雅马甲偷塞业务 `if -> then`、自然语言截胡、黑盒转译中间件、拍脑袋截断阈值或遇错擅自掐流程（参见 `first-principles-code-review` 的 `references/five-patch-mirrors.md`）。

### 关口 3 · 动笔前必先寻找行业最佳实践——严格遵守「素描模特原则」
> **核心心法（素描模特原则）**：
> 如果当前研究的问题存在**明确可靠的开源代码**，允许且鼓励先去阅读、拆解对方的代码结构，评估其模块分层、状态机与边界处理是否适用于本项目。
> **原则上，除非用户明确授权，绝不直接引用、复制或把别人的开源代码当依赖引入自家仓库。**
> 之所以要看可靠的开源代码，是因为它就像**画画时摆在面前的“素描模特”**——让你照着真实世界跑通的比例和结构去原创落笔，而不是凭自己脑子凭空脑补现实中不存在的东西，从而把 AI 写代码的幻觉概率压到最低。

严格按 [references/best-practice-playbook.md](references/best-practice-playbook.md) 完成四步寻源，并在整改方案与 PR 中**明示对照结论**：
1. 先翻自身底层框架/脚手架**真源码**；
2. 寻找明确可靠的开源“素描模特”与权威官方文档，对照拆解其代码结构并评估适用性（绝不未经用户明确授权直接引用/搬运他方代码）；
3. 提示词遵循**「先忠后改」**，自研代码遵循**「逐接口核实本仓，绝不造虚幻接口」**；
4. 外部交叉检索验证关键前提与 100 倍量级承压能力。

### 关口 4 · 重大改动先亮清「代码层改造清单与代价」
- 概念聊一致了 ≠ 代码改法也一致。凡涉及多模块改造、结构调整或带业务/体验代价的黄灯方案，**动笔前必须先向决策者摊开具体的代码层改造清单与真实代价**（用生活大白话讲透），拍板后再开工；无代价的纯技术修复则按绿灯直接闭环。

## 四、第三步：落地验收、沉淀「活态错题本」并同步回 GitHub 正本

1. **隔离分支施工 + 独立双检**：基于最新 GitHub `origin/main` 开独立分支 / `git worktree` → 先查图谱再逐行读真源码落笔 → 跑通机械门禁与真实测试 → 交由**独立非作者会话**执行 `first-principles-code-review` 拿到锁定精确 `commit SHA` 的 `【合宪放行】` → 涉用户可见链路时清零旧状态走 `visual-blackbox-review` 复测通关。
2. **反哺 GitHub 正本与活态错题本（同船合入，绝不两边断档）**：
   - 凡新确立的硬原则、接口字段或边界，必须**在同一个 PR 里**回写进 `AGENTS.md` / `BOUNDARIES.md` / `PROTOCOL_FIELDS.md` 与 `docs/decisions/`；
   - **活态错题本积累纪律**：仅当本次教训追出了通用缺失原则（思维跃迁）或暴露出跨模块反复换皮的顽固镜子时，提炼 1 条写入 `MISTAKE_BOOK.md` 并注明 PR 编号——**绝不记已修老 Bug 流水账**；已被编译器或门禁彻底锁死的旧错题及时做减法卸载。

## 五、双轨交付：问题根源外置 Markdown 交接单 + 面向用户的去代码化讲解

完成架构师根因复盘与整改设计后，**严禁只把满屏代码和字段名塞在聊天框里**，必须严格执行**双轨交付**：

### 轨 1 · 外置成独立 Markdown 交接单（给新对话 / 更高智力的 Agent 直接接手审查）
- 按 [templates/ROOT_CAUSE_HANDOFF.md](templates/ROOT_CAUSE_HANDOFF.md) 把问题根源完整外置落盘至仓库 `docs/handoffs/<YYYYMMDD>-<主题>-root-cause.md`（并随流程留痕于 GitHub）。
- **必须包含接手所需的全部精确上下文**（让用户直接把这 1 个 Markdown 文件扔给另一个更高智力的 Agent 就能秒接手，不用来回复制背景）：
  1. **代码仓与定位元数据**：GitHub 仓库地址、本地代码仓绝对路径、当前分支、精确 `commit SHA`、涉及的精确文件路径与行号；
  2. **架构师根因与全仓风险表**：错题维度定性、缺失的底层架构原则、全仓查一再查十扫出的全部兄弟点位、发现盲区自省与四方同步清单；
  3. **一手现场证据与关键真源码摘录**：真实报错堆栈/日志与核心代码片段；
  4. **底座与开源“素描模特”对照结论 + 推荐方案清单 + 请高智力 Agent 重点审查的 1–3 个核心问题**。

### 轨 2 · 聊天中面向用户的表达（默认用户不懂代码 · 解释细节 · 去代码去字段 · 沿用唯一比喻）
- **默认用户不懂代码和编程**：绝不甩出一句空洞结论敷衍了事，而是把“问题一步步是怎么发生的、根源卡在哪个环节、推荐方案怎么解决、有没有副作用或代价”的**关键细节讲清楚**；
- **彻底去代码化、去字段化**：聊天回复中不堆砌变量名、数据库字段名、表名、接口路径、英文缩写和代码行号（这些全部已经收进轨 1 的外置 Markdown 文件里）；
- **严格沿用本项目唯一比喻词典**：先查阅 `PRODUCT_BLUEPRINT.md` §1.2 中基于项目真实代码逻辑敲定的固定比喻词典，**通篇使用同一套比喻讲透细节**，绝不每次换一套新比喻增加用户认知负担，并在末尾附上外置 Markdown 文件路径方便用户随时转发给更高智力的 Agent 复核。
