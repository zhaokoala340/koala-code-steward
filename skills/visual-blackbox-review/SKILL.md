# 纯视觉黑盒审查机制（Visual Black-Box Review）

> **为什么不能只信单元测试？**
> 后台几百个模拟单测（Mock Test）全亮绿灯，往往掩盖着最致命的“半截管道病”：前后端字段名拼错、界面按钮点不动、流式交互一并发就串话、卡片弹出原始 JSON 乱码、或者只写了后端接口却漏画给用户点的确认按钮。
> 真正能穿透账面假绿的，只有**不看代码、只看屏幕、像真实付费用户一样去点去用的纯视觉黑盒审查**。

---

## 一、什么情况下应该走视觉审查？（触发边界矩阵）

不要凭感觉决定测不测，按以下明确规则执行：

### ✅ 必须触发视觉审查（满足任一条即触发）
1. **跨层改动**：改动同时跨越前端展示/交互与后端接口、实时推送（WebSocket / SSE）或存储协议。
2. **核心主链路改造**：新增或重构核心流程、提示词底座、工具调用链、多角色协作、审批/权限护栏、多模态文件处理或支付计费体验。
3. **批量合入准备发布**：连续合入多笔变更后，在正式推向生产环境前做全链路实战体检。
4. **修复人工/用户先踩出的可见故障**：必须用纯视觉黑盒复验确认真正修通，而不是只补一行单测交差。

### ⏭️ 免触发例外（不搞形式主义）
- 纯文档、注释或 README 修改；
- 纯后端底层算法重构且补充了完备确定性单测、对用户可见交互与接口协议零变动；
- 线上 **P0 紧急止血**（如全站白屏、主服务宕机、资金异常）：止血第一，先恢复上线再补视觉复测。

---

## 二、开测前不可省略的硬前提：彻底清零防“缓存假绿”

在启动任何一轮视觉审查（尤其是修复后的二轮复测）之前，**必须执行彻底清零**，严禁复用上一轮残局：
1. **清空测试数据与旧任务**：为本轮验收创建全新干净的测试账号/沙盒空间（或彻底清库重置），防止历史残留数据让本应失败的新流程“侥幸通过”。
2. **刷新服务端进程内存缓存**：重启或清空测试环境内存态，确保跑的是最新代码和冷启动真实状态。
3. **隔离浏览器工作目录与会话态**：为本次视觉测试分配全新的浏览器 Profile / 空白工作目录，不携带上一轮残留的 Cookie、LocalStorage 或登录态。
4. **隔离代码仓库访问权**：运行视觉审查的外部 Agent 或独立进程，其工作目录必须与代码仓物理隔离，从机制上杜绝偷看源码。

## 三、审查时应该代入什么身份？（真实付费用户身份构建法）

视觉审查最怕跑成“照着开发写的路径机械点一遍”。审查官**绝不能代入开发者身份**，而必须严格代入以下复合身份：

### 1. 核心人设：一位花真钱、没耐心、重结果的严苛真实用户（或企业付费老板）
- **自带真实且有冲突的业务剧本**：为审查官虚构一套完整自洽的业务背景资料（例如：真实感强的商品/课程价目表、退费红线、严禁对外透漏的保密条款，以及**测试中途临时涨价、临时推翻旧规矩**的真实业务折腾）。
- **天然反感废话与半成品**：讨厌工程黑话、讨厌“收到，我马上去办”的空头客套、讨厌需要自己猜哪里能点。

### 2. 四条纯黑盒铁律
1. **纯视觉、纯黑盒操作**：只通过真实浏览器（Playwright / 自动化浏览器 / 人工实操）进行点击、输入、上传、下载、刷新、切标签页，并同步查看浏览器 Console 报错与 Network 4xx/5xx；**严禁读取/修改代码仓库、严禁连数据库或登服务器看实现**。
2. **零脑补、零美化**：每一项场景必须亲眼在页面上看到真实渲染结果和下载到的非空文件，才能标 `PASS`；环境条件不具备如实标 `BLOCKED`，绝不靠“接口返回了 200”脑补页面正常。
3. **唯一结果北极星标准**：系统内部借口有一万个，对用户只有一个标准——**指令发出去后，在最终真正收到的可见界面或回复里，有没有拿到真实结果？**
   - “收到 / 我正在处理 / 已转交”等过程客套 → 一律不算结果；
   - 数据加载中或读取失败时显示兜底假 `0` → 判失败；
   - 没真正办完却提前标“已完成” → 判 P0 假完成。
4. **必须包含“多线并发 + 故意捣乱”施压**：
   - **多标签页并发**：同时开 2–4 个标签页并发操作，专门抓串话、状态覆盖、流式断连、重复扣款与锁死；
   - **故意捣乱与故障注入**：传假后缀文件（纯文本改成 `.png`/`.pdf`）、在流式输出 2 秒时猛点停止、审批弹窗故意点“拒绝”看系统是否偷偷绕过、尝试越权访问或输入异常边界值。

## 四、四阶段视觉审查闭环（发现 → 交叉归因 → 收敛复测）

1. **阶段 1 · 清零部署并生成审查指令单**：
   - 清空测试环境旧状态，备好全新测试账号与充足额度；
   - 读取 [templates/visual-qa-brief.md](templates/visual-qa-brief.md)，填入本次测试地址、账号、重点变更项与定制边界场景，生成本轮审查指令单。
2. **阶段 2 · 派独立视觉审查官实测并回收分级战报（回写 GitHub 留痕）**：
   - 交由独立于开发者的浏览器 Agent（如独立 Codex / ChatGPT / Claude / Playwright 评审会话）或独立测试人员执行，要求严格按战报模板输出 `PASS / FAIL / PARTIAL / BLOCKED` 与 `P0 / P1 / P2` 缺陷单（含精确复现步骤 + 截图/Console/HTTP 证据 + **被测版本的精确 `commit SHA`**）；
   - 将战报与缺陷单同步沉淀至对应 **GitHub PR / Issue**，确保后续整改 Agent 与其他协作 Agent 共享同一份现场事实，绝不把验收结论留在孤立聊天窗口里造成断档。
3. **阶段 3 · 前后端交叉定位，立即转入「追原则归因」**：
   - 将黑盒战报与测试机服务端日志、数据库/账本遥测交叉印证；
   - **严禁直接逐条糊 Bug！** 立刻激活 `root-cause-and-best-practices` Skill，追出缺失的底层原则、全仓查一再查十、升维整改并过 `first-principles-code-review` 独立审码。
4. **阶段 4 · 复测收敛判据（最多自动循环 2 轮）**：
   - 存在任一 **P0**（白屏/宕机/资损/越权泄密/假完成）或 **P1**（核心主链路失效/状态打架/未捕获 5xx）→ 必须修复、彻底清零后启动第 2 轮复测；
   - 超过 2 轮仍未收敛，或修复触及黄灯边界（改核心表/协议/权限/商业取舍）→ 停手交 5 行白话决策卡请决策者拍板；
   - **P0 = 0、P1 = 0**、服务端零崩溃、核心目标场景全绿 → 准予用**同一验证过的 commit SHA**发布上线。
